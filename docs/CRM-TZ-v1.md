# Техническое задание: внутренняя CRM для заявок и действий с сайта (MVP)

**Версия документа:** 1.0  
**Язык интерфейса:** русский  
**Часовой пояс отчётов и отображения дат:** Москва (МСК). Рекомендуется хранение времени в UTC в базе данных, отображение пользователю и фильтры по периоду — в московском времени.

---

## 1. Цель и задачи

**Цель:** единая система учёта лидов с сайта, фиксации целевых действий пользователя, ведения простой воронки продаж и базовой статистики.

**Задачи в рамках MVP:**

- Приём данных с сайта по защищённому API (форма-опрос и отдельные события).
- Хранение лидов, ответов анкеты, телефона, источника и UTM-меток при наличии.
- Ручное ведение воронки одним менеджером с историей смены статусов.
- Веб-админка на русском языке: просмотр списка, карточка лида, редактирование допустимых полей, смена статуса.
- Дашборд и отчёты: объёмы за период, распределение по статусам, простая воронка, разрезы по источнику и UTM при заполненных полях.

---

## 2. Объём MVP и границы

**Входит в MVP**

- Форма на сайте в виде короткого опроса. Все вопросы опроса обязательны для отправки.
- На сайте поле «ФИО» не показывается и не собирается. В CRM поле ФИО заполняется вручную менеджером при работе с лидом.
- Учёт клика по телефону: при нажатии на ссылку вида tel:+7… или на эквивалентную кнопку звонка сайт отправляет на API событие типа phone_click. Факт реального телефонного соединения в MVP не фиксируется; интеграция с АТС и коллтрекинг не входят в MVP.
- Одна учётная запись менеджера с полным доступом к просмотру и редактированию всех полей, для которых в системе предусмотрено редактирование, и к ручной смене статуса воронки.
- Воронка из четырёх статусов, перечисленных в разделе 5.
- Базовая статистика с привязкой отображения дат и периодов к МСК.

**Не входит в MVP**

- Подключение телефонии, автоматическая фиксация входящих звонков, запись разговоров.
- Несколько менеджеров, раздача ответственного, разграничение прав по ролям (кроме одного пользователя-менеджера).
- Несколько параллельных воронок, сложные автоматизации и сценарии.
- Отдельное мобильное приложение под CRM.

---

## 3. Роли и доступ

Предусмотрен один тип пользователя админки: менеджер. Один пользователь достаточен на этапе MVP.

Менеджер выполняет вход в систему по паролю (механизм смены пароля описывается при реализации). Менеджер просматривает список лидов, открывает карточку, вручную вводит и правит ФИО и прочие редактируемые поля, меняет статус воронки, просматривает историю статусов и раздел отчётов.

---

## 4. Форма на сайте: опрос перед отправкой лида

Все перечисленные ниже пункты обязательны. Отправка формы без ответа на любой из пунктов или с некорректными данными должна блокироваться на стороне клиента и повторно отклоняться на стороне сервера при приёме API.

**Вопрос 1.** На какую зону вы хотите пересадить волосы? Тип ввода: либо свободный текст, либо выбор из справочника зон, согласованного с заказчиком; допускается вариант «Другое» с полем для уточнения, если так решит заказчик.

**Вопрос 2.** Укажите ваш пол. Тип: выбор из фиксированного списка. Рекомендуемый набор значений для утверждения заказчиком: мужской, женский, предпочитаю не указывать.

**Вопрос 3.** Проводилось ли ранее хирургическое восстановление волос? Тип: выбор из вариантов да и нет. При необходимости заказчик может добавить вариант «не знаю» отдельным решением.

**Вопрос 4.** В каком городе удобнее посетить консультацию? Тип: выбор из списка городов. Минимальный состав списка для согласования: Сочи, Пятигорск. Полный перечень городов заказчик утверждает отдельно.

**Вопрос 5.** Оставьте номер телефона для связи. Тип: телефон. Поле обязательно. Формат ввода и нормализация на сервере (например приведение к единому виду для поиска дублей) согласовываются при реализации.

После успешной отправки в CRM создаётся лид со статусом «Первый контакт». Пользователю показывается подтверждение успеха. При ошибке сервера пользователю показывается нейтральное сообщение, детали ошибки пишутся в серверные логи.

---

## 5. Воронка продаж

Статусы лида фиксированы и перечислены в логическом порядке ведения сделки:

1. Первый контакт — статус, который присваивается лиду при создании из формы сайта.
2. Переговоры.
3. Принимают решение.
4. Подписание договора.

Менеджер вручную переводит лид в любой из статусов. Ограничения на обратный переход статуса в MVP не задаются, если заказчик отдельно не потребует запретить откат назад.

Каждая смена статуса записывается в историю: дата и время в МСК, предыдущий статус, новый статус, идентификатор пользователя, выполнившего смену (для одного менеджера поле всё равно сохраняется для будущего расширения).

---

## 6. События с сайта помимо формы

**Событие клика по телефону.** При клике по ссылке tel или по кнопке, открывающей тот же номер, фронтенд отправляет на API событие с типом phone_click. В теле события передаётся как минимум номер из href или эквивалент, отметка времени. При реализации на сайте допускается передача анонимного идентификатора сессии для возможной связи клика и последующей отправки формы в одной пользовательской сессии; это не обязательное требование, но полезное уточнение для аналитики.

Никаких утверждений о факте голосового вызова в MVP не делается.

---

## 7. Состав данных лида в CRM

Система хранит ответы на все пять вопросов опроса в разрезе, удобном для фильтрации и отчётов (отдельные поля в базе или структурированное хранение с дублированием в текстовом блоке анкеты для удобства менеджера — на усмотрение разработки при условии сохранности данных).

Хранится телефон. Политика дублей по одному и тому же номеру (запрет второго лида, разрешение нескольких заявок с меткой времени, слияние карточек) утверждается заказчиком до финализации модели данных.

Хранится дата и время создания лида с отображением в МСК.

Хранится источник: указание на сайт и при передаче с фронта — URL страницы, с которой отправлена заявка.

При передаче с сайта поддерживаются необязательные поля UTM: utm_source, utm_medium, utm_campaign, utm_content, utm_term.

В карточке лида есть поле ФИО. Оно не заполняется из формы сайта и заполняется или изменяется только вручную менеджером в админке.

Рекомендуется поле внутренних комментариев менеджера к лиду в MVP для фиксации результатов звонков и договорённостей.

Связанные события с сайта, в частности phone_click, отображаются в карточке или в отдельной ленте активности лида — на усмотрение проектирования интерфейса при условии доступности информации менеджеру.

---

## 8. Админка: функции MVP

Список лидов в виде таблицы. Минимальный набор колонок для отображения согласовывается при вёрстке, но должен позволять менеджеру ориентироваться без открытия карточки: дата создания, телефон, статус, город из анкеты, краткая информация по зоне или первый вопрос, наличие или отсутствие введённого ФИО.

Фильтры: календарный период в МСК, статус воронки, город, значение пола из анкеты, при наличии данных фильтр по источнику или UTM.

Карточка лида: просмотр всех ответов анкеты, ручной ввод и правка ФИО, комментарии менеджера, смена статуса, просмотр истории смены статусов.

Выход из системы. Базовая защита от несанкционированного доступа.

## 9. Статистика и отчёты MVP

Количество новых лидов за выбранный период в МСК.

Распределение лидов по статусам на выбранную дату или за период.

Простая воронка: число лидов на каждом этапе и при наличии истории статусов — отчёт по переходам между этапами за период.

Разрез по источнику и по заполненным UTM-полям.

Экспорт в CSV не входит в обязательный MVP, может быть вынесен в версию 1.1 по согласованию.

## 10. API для приёма данных с сайта

Все вызовы только по HTTPS.

Секрет для вызова API не размещается в коде страницы в браузере. Сайт отправляет данные на собственный backend или на выделенный endpoint с прокси, а уже серверная часть обращается к CRM API с ключом из переменных окружения либо использует единый backend CRM, если форма и API совмещены в одном приложении.

Формат тела запросов и ответов: JSON, кодировка UTF-8.

Логика разделения: отдельный метод создания лида по результатам опроса и отдельный метод регистрации событий, например phone_click. Конкретные пути вида POST /api/v1/leads и POST /api/v1/events задаются при проектировании, но требования к поведению остаются: создание лида со статусом Первый контакт, запись всех пяти ответов и телефона, запись UTM и источника при наличии.

Успешное создание лида: код ответа 201 и идентификатор созданного лида в теле ответа либо эквивалент, согласованный при реализации.

Ошибка валидации: код 422 и перечень полей с описанием ошибок.

Отсутствие или неверный ключ: код 401 или 403.

Превышение частоты запросов: код 429 и при необходимости заголовок с указанием времени повтора.

На стороне приёма заявок реализуются ограничение частоты запросов по IP и по нормализованному телефону, опционально подключение CAPTCHA или аналога по решению заказчика.

## 11. Нефункциональные требования

Регулярное резервное копирование базы данных. Периодичность и место хранения бэкапов согласовываются с заказчиком.

Логирование ошибок приложения и неуспешных вызовов интеграции.

Требования законодательства о персональных данных, в том числе 152-ФЗ: цели обработки, срок хранения, политика конфиденциальности на сайте, механизм обращений субъекта данных — оформляются совместно с заказчиком и при необходимости с юристом.

Требования к доступности сервиса и выбор площадки хостинга согласовываются отдельно.

---

## 12. Критерии приёмки

Успешная отправка полностью заполненного опроса с валидным телефоном создаёт в системе лид со статусом Первый контакт, все пять ответов отображаются в карточке без потерь.

Попытка отправки с пропуском любого вопроса или с невалидным телефоном отклоняется, пользователю показывается понятное сообщение, на сервере лиды с некорректными данными не создаются.

Клик по телефону на сайте приводит к записи события phone_click с корректным номером из ссылки.

Менеджер вводит ФИО в карточке, сохраняет, после обновления страницы данные сохранены.

Смена статуса отражается в истории с корректным временем в МСК.

Отчёт за выбранный период согласуется с ручной проверкой выборки по тем же фильтрам дат в списке лидов.

Запрос к API создания лида или события без действительного ключа авторизации отклоняется.

## 13. Открытые решения до старта разработки

Утвердить способ ввода зоны пересадки: только текст или фиксированный справочник с вариантом «другое».

Утвердить окончательные наборы значений для пола и для вопроса о прошлой хирургии.

Утвердить полный список городов для вопроса о консультации.

Утвердить политику дублей по телефону.

Утвердить необходимость CAPTCHA или аналога в MVP.
